## 0. 为什么插入 M1.5

原路线 M1 → M2（治理面）。但实测盘点发现两条事实：

1. **效果面欠账比治理面更影响可用性**。本地模型每秒几十 token、响应非流式
   （[openai_compat.py](../packages/agent-core/agent_core/llm/openai_compat.py) 写死 `"stream": False`），
   一次 30 秒的生成期间 UI 无任何反馈；会话纯内存（[host/session.py](../packages/agent-core/agent_core/host/session.py)），重启即丢。
   这两点不解决，给同事用一天就会弃用。
2. **没有回滚就没有"敢放手"**。Agent 改坏文件后无法一键回退，审批闸门只能防"未发生"，
   不能救"已发生"。`Config.checkpoint_dir` 已预留（[config.py L133](../packages/agent-core/agent_core/config.py#L133)）但零实现。

因此 M1.5 的唯一目标：**单人/小团队真实日常使用的最后一公里**。
治理面（M2，`apps/server/vibe_server` 的 schema 已开工）在 M1.5 期间保持冻结，避免两线作战。

### C4 上下文裁剪升级：删除前摘要（P2，可选）

**现状**：`_trim_context()`（[agent.py L307](../packages/agent-core/agent_core/loop/agent.py)）超预算时**整块删除**最早轮次，信息直接丢失。

| 子任务 | 内容 | 状态 |
|---|---|---|
| C4.1 | 开关：`Config.compact_on_trim: bool = False`（`VIBE_COMPACT_ON_TRIM`），默认关——先用 C1/C3 把上下文质量做上去，摘要属锦上添花 | ✅ |
| C4.2 | 实现：裁剪前把待删除轮次交给**当前模型**生成 ≤ 500 字摘要，存为一条 `system` 级 memory 消息置于队首；摘要调用失败则退回纯删除（现状行为），不阻塞主流程 | ✅ |
| C4.3 | 审计：`context.compact` 事件，记被压缩轮数与摘要长度 | ✅ |

**验收**：开启后长会话中早期结论（如"用户要求不用第三方库"）在裁剪后仍能被模型引用；关闭时行为与现状逐字节一致。

**结论（2026-09-24 落地）**：功能已上线、默认关。验收由
`packages/agent-core/tests/test_compact.py`（19 条）钉住：开启时摘要装在
`messages[1]`（紧跟系统提示）、下一轮模型可见的上下文里能找到早期结论；
关闭时零次摘要调用、删除条数与最老幸存消息逐条等于旧实现。落地时有四处
设计取舍值得记一笔：

1. **干跑规划再删**（`_plan_trim`）。删除不可逆，而摘要可能失败 —— 先把
   「删哪些」算出来但不落地，摘要成功才 `del`，失败就干净地退回纯删除。
   边删边数的话，摘要失败时历史已经被改了，没法退。
2. **摘要正文只存一份**，直接放在 `messages[1]` 里，不另存
   `self._memory_summary` 字段。两份状态迟早漂移，而「摘要是否在位」
   恰好可以当成裁剪起点的判据（`_trim_start`）。
3. **上一版摘要要喂回摘要请求**。否则第二次裁剪会把第一轮定下的约束
   覆盖掉 —— 而「早期结论跨多次裁剪存活」正是这个功能的验收点。
   新摘要是对新旧信息的再压缩，上限不变，所以它不随裁剪次数增长。
4. **提示输入两头夹紧**（单条 800 / 总量 8000 字符）。裁剪预算默认 12 万
   字符，把待删历史原样塞进摘要请求大概率被上游按上下文超限拒掉，
   而它一失败就退回纯删除 —— 等于开关悄悄不生效。

另：摘要**不持久化**（不走 `_record`）。它是派生内容，每次裁剪都会重算，
而裁剪本身不动会话库 —— 进程重启后历史从库里完整恢复、按同一套规则重新裁。
存下来的摘要只会变成一份重复的旧快照。

**已知边界**：摘要质量取决于当前模型，小模型可能不守 500 字上限（因此加了
硬截断）；关闭开关时摘要开销为零，开启后每次触发裁剪会多一轮模型调用，
会计入 `RunStats` 的 token 统计。

## 7. 补记（2026-09-28）

### W1 Web 界面内的「打开文件夹作为工作区」入口 —— ✅ 已实现

M1 的桌面壳只有原生菜单能切工作区（写配置 → `app.relaunch`），**浏览器预览里没有入口**。
本次在 host 侧补齐：`GET /api/workspaces`（最近列表）+ `POST /api/workspaces/open`。

关键约束：`Config.workspace` 在启动时就绑定了 PathGuard、检查点目录与审计哈希链
（`<workspace>/.vibe/audit.jsonl`），**不能原地改字段**（会让"审计链已推进"与"jail 已换根"
互相矛盾），故切换 = 造新 `Config` 再换掉整个 `Session`，复用同一条 EventBus 推
`session.ready` 保证 SSE 不掉线；旧链以 `session.end("workspace_switch")` 收尾，新链在新
工作区重新 `session.start` —— 两条链各自完整、互不污染。桌面壳统一走该接口，失败回退
`app.relaunch`。

落地清单与验收见 `docs/M2-PLAN.md` §6，架构侧口径见 `docs/ARCHITECTURE.md` §6「M1.5 实际落地情况」。

**补充（同日）：浏览器侧的目录选择不再是「手输绝对路径」。** 上一版只给了路径输入框 +
最近列表，理由是浏览器拿不到系统目录对话框（File System Access API 给不出真实路径）。
实际用起来这一条等于「要用记得住完整路径」，所以又补了一个**内置目录浏览器**：
host 新增只读接口 `GET /api/fs/dirs?path=...`（空 `path` 列盘符，Windows 下额外给一个
主目录入口），返回当前路径、上级路径与**直接子目录名**；切换工作区弹窗里可逐级点进去、
也可用「上级」退回（到盘符根时退回盘符列表）。

两条边界必须写清楚，否则后面很容易被误改：

- **这个接口刻意不过 `PathGuard`** —— 它服务的正是「挑一个当前 jail 之外的新工作区」，
  用 jail 去卡它等于让功能永远不可用。它的边界改由 host 闸门兜住（只监听本机 + 每次启动
  的随机 token + Host/Origin 双校验），并且**只回传目录名、不读任何文件内容**，因此与
  「界面能看到的文件范围 = Agent 能读到的范围」那条原则不冲突（目录名不是文件内容）。
- 路径不存在/不是目录 → 400（客户端输入问题），无权限读取 → 403；解析用 `resolve()`，
  符号链接目录不跟随（避免把用户带出可预期的范围）。

于是目录选择在浏览器与桌面壳里是**两条平行的路**：壳内是原生对话框
（`vibeShell.pickFolder()`，按钮只在壳内出现），浏览器内是内置浏览器 —— 两者最终都只是
把路径填进同一个输入框，切不切仍由用户按「切换并重启」决定。
